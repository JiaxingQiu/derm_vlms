# Assignment System

How lesions are assigned to annotators, and why it's safe.

## Design goals

1. **Deterministic** — same seed + same eligible lesions = identical assignments.
2. **Immutable** — once a user registers, their lesion list never changes.
3. **Decoupled** — assignment data is generated locally and deployed as a
   static file; the server never recomputes assignments.

## Architecture

```
─────                               ────                    ──────
parsedata                           Azure Blob              download_from_blob.py
  ├─ annotations_data.json   ──►    deploy/data/     ──►    revlm_dc/data/

```

## The slot file: `assignment_slots.json`

Generated by `python manage.py parsedata` (locally, once).

Contains 500 pre-computed slots, each with a fixed list of 101 `case_id`s.
The first case in every slot is always the **anchor lesion** (`1025_combined`)
which serves as a warmup/calibration case.

```json
{
  "seed": 42,
  "n_slots": 500,
  "eligible_lesion_count": 350,
  "cases_per_slot": 101,
  "created_at": "2026-06-10T...",
  "slots": [
    {"slot": 0, "case_ids": ["1025_combined", "42_combined", ...]},
    {"slot": 1, "case_ids": ["1025_combined", "99_combined", ...]},
    ...
  ]
}
```

**Idempotent**: re-running `parsedata` with the same CSVs and seed produces
a byte-identical file (except for `created_at`).

## How slots are computed

Each slot uses a synthetic user id (`slot_000`, `slot_001`, ...) and the
existing bucket-based priority sampling in `_select_lesions_for_user`.
Slots are computed sequentially so each slot's selection accounts for the
lesion counts accumulated by all prior slots, maximising coverage.

Key parameters (in `ROLE_CONFIG`):

| Parameter | Value | Meaning |
|-----------|-------|---------|
| `lesions_per_user` | 101 | Cases per annotator (1 anchor + 100 random) |
| `min_annotators` | 3 | Target minimum annotators per lesion |
| `max_annotators` | 5 | Hard cap per lesion |
| `need_more_cap` | 50 | Max under-covered lesions to backfill per user |

## Registration flow

When a new user registers:

1. `next_available_slot(role)` finds the lowest slot number not yet claimed
   (checked via `assignment_slot` field on the user model).
2. The user is created with `assignment_slot = <slot>`.
3. `assign_from_slot(evaluator, slot, role)` reads the case list from
   `assignment_slots.json` and writes `Assignment` rows to the DB.

All of this happens inside a `transaction.atomic()` block with
`select_for_update()` to prevent race conditions.

**After this point, the user's assignments are never modified.**

## Test accounts

`test` and `test_pcp` always use **slot 0**. Their assignments are
re-written from slot 0 on every login (along with annotation reset).
This is intentional — test accounts are throwaway.

Slot 0 is never claimed by `next_available_slot()` for real users because
test accounts do not have `assignment_slot` set via the normal registration
path (they use `get_or_create` and hard-coded slot 0).

## What NOT to do

- **Never run `generate_assignments` on the server.** It uses the old
  dynamic path and would overwrite everyone's assignments.
- **Never run `parsedata` on the server.** Data artifacts are produced
  locally and uploaded via blob.
- **Never manually modify `assignment_slots.json`** after users have
  started annotating. If you need to change assignment logic, generate a
  new file and verify it against existing user assignments.

## DB fields

Both `Dermatologist` and `PCPUser` models have:

- `assignment_slot` (`PositiveIntegerField`, nullable) — which slot this
  user was assigned. `NULL` for legacy users or test accounts.

The `Assignment` / `PCPAssignment` tables store the actual case list:

- `evaluator` (FK to user)
- `case_id` (e.g., `"1025_combined"`)
- `order` (0-based position)

## FAQ

**Q: What if we need more than 500 users?**
A: Increase `MAX_SLOTS` in `assignments.py` and re-run `parsedata` locally.
Slots 0–499 will be identical; new slots 500+ will be appended.

**Q: What if the eligible lesion list changes (new predictions)?**
A: Re-run `parsedata`. Existing users' DB assignments are untouched.
New registrations will use the updated slot file. Note: if lesions are
removed, existing assignments may reference case_ids no longer in
`annotations_data.json` — handle this at the view layer if needed.

**Q: Can I verify assignments are correct?**
A: Use `generate_assignments --dry-run` to recompute and compare against
the slot file, or query the `Assignment` table directly in the Django admin.
